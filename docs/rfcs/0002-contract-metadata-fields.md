# RFC 0002: Contract Metadata and Traceability Fields

**Status:** Draft
**Issue:** [#63](https://github.com/afewell-hh/hoss/issues/63)
**Author:** HOSS Team
**Created:** 2025-10-13
**Updated:** 2025-10-13

## Summary

Extend the HOSS result envelope with metadata fields for tool versioning, container provenance, artifact mapping, and per-target execution timing. These fields enable reproducibility, supply chain verification, UI integration, and performance analysis.

## Motivation

**Current State (v0.1.0):**

```json
{
  "status": "ok",
  "validated": 1,
  "warnings": 0,
  "failures": 0,
  "tool": {
    "name": "hhfab",
    "version": "0.41.3"
  }
}
```

**Missing Information:**
- **Reproducibility:** No git SHA for hhfab version (can't pin exact version)
- **Provenance:** No container digest (can't verify supply chain)
- **Traceability:** No mapping between result envelope and `.artifacts/` files
- **Performance:** No per-target timing data (can't identify slow validations)

**User Pain Points:**

1. **Security Teams:** "Which hhfab container was used? How do I verify it?"
2. **Support Engineers:** "Where are the detailed logs for this validation?"
3. **Performance Engineers:** "Which topology is causing the 30s delay?"
4. **Reproducibility:** "How do I re-run this exact validation 6 months from now?"

## Design

### Result Envelope Schema Extensions

```json
{
  "status": "ok",
  "validated": 1,
  "warnings": 0,
  "failures": 0,
  "tool": {
    "name": "hhfab",
    "version": "0.41.3",
    "gitSha": "abc1234567890abcdef1234567890abcdef1234",
    "gitShort": "abc1234",
    "containerDigest": "ghcr.io/afewell-hh/hoss/hhfab@sha256:54814bbf4e8459cfb35c7cf8872546f0d5d54da9fc317ffb53eab0e137b21d7b",
    "platform": "linux/amd64"
  },
  "matrix": {
    "enabled": true,
    "concurrency": 4,
    "executionTimeMs": 8734,
    "targets": [
      {
        "path": "samples/topology-basic.yaml",
        "status": "ok",
        "validated": 1,
        "warnings": 0,
        "failures": 0,
        "executionTimeMs": 2341,
        "artifactPaths": [
          ".artifacts/target-0/validation.log",
          ".artifacts/target-0/topology-parsed.json"
        ],
        "checksum": "sha256:a1b2c3d4..."
      }
    ]
  },
  "execution": {
    "startTime": "2025-10-13T14:32:01.234Z",
    "endTime": "2025-10-13T14:32:10.968Z",
    "hostname": "runner-abc123",
    "workspace": "/workspace"
  }
}
```

### Field Definitions

#### tool.gitSha (optional)
- **Type:** String (40-character hex SHA)
- **Description:** Git commit SHA of hhfab tool
- **Source:** `hhfab --version` output or `HHFAB_GIT_SHA` env var
- **Example:** `"abc1234567890abcdef1234567890abcdef1234"`
- **Fallback:** `null` if unavailable

#### tool.gitShort (optional)
- **Type:** String (7-character hex SHA)
- **Description:** Short git commit SHA (first 7 chars)
- **Source:** Derived from `tool.gitSha`
- **Example:** `"abc1234"`
- **Fallback:** `null` if gitSha unavailable

#### tool.containerDigest (optional)
- **Type:** String (full digest reference)
- **Description:** Complete container digest including registry/repo
- **Source:** `HHFAB_CONTAINER_DIGEST` env var (set by Demon or CI)
- **Example:** `"ghcr.io/afewell-hh/hoss/hhfab@sha256:54814bbf..."`
- **Fallback:** `null` if not running in container

#### tool.platform (optional)
- **Type:** String (OS/arch)
- **Description:** Platform architecture of hhfab binary
- **Source:** `uname -m` and `uname -s`
- **Example:** `"linux/amd64"`, `"darwin/arm64"`
- **Fallback:** `"unknown"`

#### matrix.targets[].artifactPaths (optional)
- **Type:** Array of strings (relative paths)
- **Description:** Paths to artifacts generated by this target's validation
- **Source:** Enumerate `.artifacts/target-N/*` after validation
- **Example:** `[".artifacts/target-0/validation.log"]`
- **Fallback:** `[]` if no artifacts

#### matrix.targets[].checksum (optional)
- **Type:** String (sha256 hash)
- **Description:** SHA256 checksum of input topology file
- **Source:** `sha256sum <topology-file>`
- **Example:** `"sha256:a1b2c3d4..."`
- **Purpose:** Verify topology file integrity, detect modifications

#### execution.startTime / execution.endTime (optional)
- **Type:** ISO 8601 timestamp string
- **Description:** Validation start/end timestamps
- **Source:** `date -u +"%Y-%m-%dT%H:%M:%S.%3NZ"`
- **Purpose:** Wall-clock timing, timezone-agnostic scheduling

#### execution.hostname (optional)
- **Type:** String
- **Description:** Hostname of machine running validation
- **Source:** `hostname` command
- **Purpose:** Identify runner in CI/CD environments

#### execution.workspace (optional)
- **Type:** String (absolute path)
- **Description:** Absolute path to workspace root
- **Source:** `pwd` at validation start
- **Purpose:** Artifact path resolution

### Backward Compatibility

**All new fields are optional:**
- Existing v0.1.0 result parsers ignore unknown fields (forward-compatible JSON parsing)
- Missing fields indicate feature unavailable (e.g., `tool.gitSha: null` means git SHA not available)
- Graceful degradation: validation succeeds even if metadata extraction fails

**Migration Path:**
- v0.1.0 results: Missing fields (old schema)
- v0.2.0 results: All optional fields populated when available
- v0.2.0 backward compat mode: Can produce v0.1.0 schema if `HOSS_LEGACY_ENVELOPE=1`

## Implementation

### Phase 1: Tool Metadata Extraction

**scripts/hoss-validate.sh additions:**

```bash
# Extract hhfab version and git SHA
HHFAB_VERSION=$(hhfab --version 2>/dev/null | grep -oP 'v\d+\.\d+\.\d+' || echo "unknown")
HHFAB_GIT_SHA=${HHFAB_GIT_SHA:-$(hhfab --version 2>/dev/null | grep -oP '[0-9a-f]{40}' || echo "")}
HHFAB_GIT_SHORT=""
if [[ -n "$HHFAB_GIT_SHA" ]]; then
  HHFAB_GIT_SHORT="${HHFAB_GIT_SHA:0:7}"
fi

# Container digest from env var (set by Demon or CI)
HHFAB_CONTAINER_DIGEST=${HHFAB_CONTAINER_DIGEST:-""}

# Platform detection
PLATFORM="$(uname -s | tr '[:upper:]' '[:lower:]')/$(uname -m | sed 's/x86_64/amd64/; s/aarch64/arm64/')"

# Build tool metadata JSON
TOOL_METADATA=$(jq -n \
  --arg name "hhfab" \
  --arg version "$HHFAB_VERSION" \
  --arg git_sha "$HHFAB_GIT_SHA" \
  --arg git_short "$HHFAB_GIT_SHORT" \
  --arg digest "$HHFAB_CONTAINER_DIGEST" \
  --arg platform "$PLATFORM" \
  '{
    name: $name,
    version: $version,
    gitSha: (if $git_sha != "" then $git_sha else null end),
    gitShort: (if $git_short != "" then $git_short else null end),
    containerDigest: (if $digest != "" then $digest else null end),
    platform: $platform
  }')
```

### Phase 2: Artifact Path Mapping

**Per-target artifact collection:**

```bash
# After validation completes for target $i
ARTIFACT_DIR=".artifacts/target-$i"
mkdir -p "$ARTIFACT_DIR"

# Collect artifact paths (relative to workspace)
ARTIFACT_PATHS=$(find "$ARTIFACT_DIR" -type f -printf "%P\n" | jq -R . | jq -s .)

# Compute topology checksum
TOPOLOGY_CHECKSUM=$(sha256sum "$topology" | awk '{print "sha256:" $1}')

# Write per-target result with metadata
jq -n \
  --arg path "$topology" \
  --argjson artifact_paths "$ARTIFACT_PATHS" \
  --arg checksum "$TOPOLOGY_CHECKSUM" \
  --argjson execution_time "$target_execution_time" \
  '{
    path: $path,
    status: "ok",
    executionTimeMs: $execution_time,
    artifactPaths: $artifact_paths,
    checksum: $checksum
  }' > "$ARTIFACT_DIR/result.json"
```

### Phase 3: Execution Metadata

**Capture execution context:**

```bash
# At validation start
EXECUTION_START=$(date -u +"%Y-%m-%dT%H:%M:%S.%3NZ")
EXECUTION_HOSTNAME=$(hostname)
EXECUTION_WORKSPACE=$(pwd)

# At validation end
EXECUTION_END=$(date -u +"%Y-%m-%dT%H:%M:%S.%3NZ")

# Build execution metadata JSON
EXECUTION_METADATA=$(jq -n \
  --arg start "$EXECUTION_START" \
  --arg end "$EXECUTION_END" \
  --arg hostname "$EXECUTION_HOSTNAME" \
  --arg workspace "$EXECUTION_WORKSPACE" \
  '{
    startTime: $start,
    endTime: $end,
    hostname: $hostname,
    workspace: $workspace
  }')
```

### Phase 4: Envelope Aggregation

**Final result.json generation:**

```bash
# Aggregate all per-target results with full metadata
jq -s \
  --argjson tool_metadata "$TOOL_METADATA" \
  --argjson execution_metadata "$EXECUTION_METADATA" \
  --argjson matrix_enabled "$MATRIX_ENABLED" \
  --argjson concurrency "$CONCURRENCY" \
  --argjson total_time "$TOTAL_EXECUTION_TIME" \
  '
  {
    status: (if all(.status == "ok") then "ok" else "failed" end),
    validated: map(.validated // 0) | add,
    warnings: map(.warnings // 0) | add,
    failures: map(.failures // 0) | add,
    tool: $tool_metadata,
    matrix: {
      enabled: $matrix_enabled,
      concurrency: $concurrency,
      executionTimeMs: $total_time,
      targets: .
    },
    execution: $execution_metadata
  }
  ' .artifacts/target-*/result.json > result.json
```

## Use Cases

### Use Case 1: Supply Chain Verification

**Actor:** Security team auditing validation results

**Flow:**
1. Receive `result.json` from CI pipeline
2. Extract `tool.containerDigest`
3. Verify digest against approved list
4. Use cosign to verify container signature

**Benefit:** Ensure only approved hhfab containers are used

### Use Case 2: Performance Analysis

**Actor:** Performance engineer investigating slow validations

**Flow:**
1. Parse `matrix.targets[].executionTimeMs` from result.json
2. Identify slowest topology (e.g., 30s vs 3s average)
3. Find artifacts using `matrix.targets[].artifactPaths`
4. Analyze `.artifacts/target-N/validation.log` for bottlenecks

**Benefit:** Pinpoint performance issues without manual artifact hunting

### Use Case 3: Reproducible Validation

**Actor:** Operator reproducing issue from 6 months ago

**Flow:**
1. Retrieve old `result.json` from archive
2. Extract `tool.gitSha` (e.g., `abc1234`)
3. Build hhfab container from that commit: `docker build --build-arg GIT_SHA=abc1234`
4. Extract `matrix.targets[].checksum` to verify topology file unchanged
5. Re-run validation with exact same hhfab version

**Benefit:** Bit-for-bit reproducible validation results

### Use Case 4: UI Integration

**Actor:** Web dashboard displaying validation results

**Flow:**
1. Parse `result.json` from validation run
2. Display per-target breakdown from `matrix.targets[]`
3. Link each target to artifacts using `artifactPaths`
4. Show timing heatmap using `executionTimeMs`
5. Display tool version badge from `tool.version` + `tool.gitShort`

**Benefit:** Rich UX without custom parsing logic

## Security Considerations

### Information Disclosure
- **Risk:** `execution.hostname` leaks internal infrastructure details
- **Mitigation:** Sanitize hostname in production (e.g., `runner-***` instead of `prod-k8s-node-42`)

### Path Traversal
- **Risk:** `artifactPaths[]` could reference files outside `.artifacts/`
- **Mitigation:** Validate all paths start with `.artifacts/`, reject `..` components

### Checksum Verification
- **Risk:** Attacker modifies topology file after checksum computed
- **Mitigation:** Compute checksum before validation starts, re-verify before reporting

## Open Questions

1. **Should we include OS-level metadata (kernel version, glibc version)?**
   - Pros: Complete reproducibility
   - Cons: Verbose, most users don't need it
   - Decision: Defer to future RFC if users request it

2. **How should artifact paths work with multi-topology mode?**
   - Current: `.artifacts/target-0/`, `.artifacts/target-1/`
   - Alternative: `.artifacts/{topology-basename}/`
   - Decision: Use `target-N` for now (predictable, no basename conflicts)

3. **Should execution metadata include env vars (DEMON_DEBUG, etc.)?**
   - Pros: Complete context for debugging
   - Cons: Risk of leaking sensitive env vars (tokens, passwords)
   - Decision: No - too risky, users can add manually if needed

## Success Metrics

- **Adoption:** ≥30% of result.json files include `tool.gitSha` within 3 months
- **Support Efficiency:** Average artifact location time reduced by 50% (from 5min to 2.5min)
- **Reproducibility:** ≥90% of old validations can be reproduced using archived metadata
- **Security Audits:** 100% of production validations include `tool.containerDigest`

## Alternatives Considered

### Alternative 1: Separate metadata.json file
**Pros:** Keep result.json clean, optional metadata file
**Cons:** Two files to manage, easy to lose association
**Decision:** Rejected - single envelope is simpler

### Alternative 2: Verbose mode only (HOSS_VERBOSE=1)
**Pros:** Keeps default result.json minimal
**Cons:** Metadata not available by default, users must opt-in
**Decision:** Rejected - metadata should be default (all fields optional)

### Alternative 3: External metadata service
**Pros:** Centralized metadata store, queryable API
**Cons:** Requires infrastructure, conflicts with Demon's stateless model
**Decision:** Rejected - too complex for v0.2.0
